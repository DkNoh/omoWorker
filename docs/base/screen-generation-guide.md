# 화면 생성 절차서 — Scaffold First

폐쇄망에서 메뉴 하나를 동작하는 업무 화면으로 만드는 표준 체크리스트다. Java·XML·HTML·JS 파일을 각각 수동으로 시작하지 않고 Query Scaffold로 기본 골격을 한 번 생성한 뒤 개발자가 완성한다.

## 0. 생성 원칙

- `.tpl`은 최초 생성 원본이다.
- 적용된 생성물은 개발자 소유다.
- 생성 이후 템플릿과의 동기화는 요구하지 않는다.
- 재생성은 기존 수정본의 업데이트가 아니라 폐기 후 신규 생성이다.
- Scaffold에 없는 기능은 생성된 기본 레이아웃과 공통 자산 위에 개발자가 추가한다.

소유권과 재생성 기준은 `docs/base/scaffold-contract.md`를 따른다.

## 1. 대상과 도메인 확정

- 메뉴 URL, 화면명, 업무 거래를 확인한다.
- 쓰기 소유 테이블 기준으로 도메인 경계를 정한다.
- LIST/EXCEL/CRUD 중 `screenMode`를 선택한다.
- 개인정보, 엑셀, 승인, 마스킹 해제 등 추가 요구사항을 기록한다.
- 현재 메뉴에 있는 테스트 화면은 운영 요구사항의 근거로 사용하지 않는다.

완료 조건: URL, 도메인, `screenMode`, 추가 기능 여부가 확정됐다.

## 2. 테이블과 조회 SQL 확인

- 실제 DB 또는 DBA 명세로 테이블, PK, 컬럼 타입을 확인한다.
- 표시 컬럼을 명시하고 `SELECT *`, `A.*`를 사용하지 않는다.
- 검색조건은 `$변수` 규약으로 작성한다.
- 결정적 `ORDER BY`와 tie-breaker를 정한다.
- CRUD라면 수정 대상 `targetTable`, 실제 PK, 잠금 컬럼, 수정 허용 컬럼을 확정한다.
- 복잡한 집계, `UNION`, CTE, 다중 쓰기 소유권은 자동 생성 적합성을 먼저 판단한다.

완료 조건: SQL이 대상 DB에서 실행되고 Scaffold 입력값이 준비됐다.

## 3. Scaffold 분석과 최초 생성

1. local 환경의 `/system/scaffold`에 접속한다.
2. 기본 정보와 조회 SQL을 입력한다.
3. **옵션 갱신**으로 검색 변수와 조회조건 화면명, 컬럼, DB comment 기반 화면명, PK와 대상 테이블 분석 결과를 확인한다.
4. 조회조건·컬럼 화면명, 그리드 표시, 등록·수정 표시와 입력 허용 여부, 날짜 형식, 마스킹과 메뉴 옵션을 조정한다. `BETWEEN` 조회조건은 시작일자/종료일자 기본값을 확인한다.
5. **생성**으로 전체 산출물을 검토한다.
6. **적용 미리보기**에서 신규/변경없음/덮어쓰기를 확인한다.
7. 기존 개발자 소유 파일의 `OVERWRITE`가 없을 때 최초 적용한다.

Scaffold가 생성하는 DTO/VO/Mapper/Service/Controller/Test/HTML/JS/메뉴 SQL을 같은 생성 계약으로 취급한다. 일부만 손으로 먼저 만들지 않는다.

## 4. 생성 직후 검토

- SearchRequestDTO 필드, 화면 검색 input, Mapper 바인딩이 일치하는지 확인한다.
- VO 필드, SELECT alias, 그리드 `columns.name`이 일치하는지 확인한다.
- DB comment가 없는 계산 컬럼의 화면명을 직접 지정했는지 확인한다.
- 조회조건 화면명이 DB comment 또는 SELECT alias에서 올바르게 연결됐는지, `BETWEEN`은 시작일자/종료일자로 표시되는지 확인한다.
- COUNT와 목록 검색조건이 같은 결과 범위를 사용하는지 확인한다.
- CRUD의 PK, 잠금 컬럼, `editable=true` 화이트리스트를 확인한다.
- 메뉴 URL과 `CAN_*` 권한이 `screenMode`에 맞는지 확인한다.
- 개인정보 컬럼의 마스킹과 감사 로그 적용 지점을 확인한다.

이 단계가 끝나면 생성된 파일은 개발자 소유로 전환된다.

## 5. 업무 기능과 화면 고유 기능 개발

생성기가 제공하지 않는 내용은 생성물에 직접 구현한다.

- 중복 검사, 상태 전이, 소유권 검사와 같은 Service 업무 규칙
- 복잡한 Mapper SQL과 추가 조회·저장 메서드
- 특수 상세보기, 팝업, 중첩 모달, 미리보기 패널, 업무별 formatter
- 외부 시스템 연계와 여러 도메인을 묶는 오케스트레이션
- 생성 테스트의 TODO를 대체하는 실제 업무 규칙 테스트

공통 그리드, HTTP, 모달, 폼 바인딩, 입력 포맷과 상세행 레이아웃은 다시 만들지 않고 프로젝트 공통 자산을 사용한다.

## 6. 메뉴와 권한 연결

- 생성된 메뉴 SQL을 검토하고 실제 상위 메뉴와 정렬 순서를 반영한다.
- `TB_MENU`와 `TB_MENU_AUTH`에 필요한 권한을 부여한다.
- 업무 URL을 Interceptor 제외 경로에 추가하지 않는다.
- 승인 업무 권한은 메뉴 CRUD 권한과 분리된 정책이 있는지 확인한다.

## 7. 검증

```text
mvn test                  PASS
mvn -DskipTests package   PASS
```

브라우저에서는 수정한 화면과 동작만 확인한다.

- 화면 진입과 LNB 활성 상태
- 검색, 초기화, 페이징과 총 건수
- CRUD 등록·수정·삭제 및 충돌 처리
- 권한별 버튼 표시와 API 403
- 개인정보 마스킹과 원문 조회 권한
- 추가한 팝업·모달·외부 연계 동작

미검증 항목은 완료가 아니라 부분 완료로 보고한다.

## 8. 재생성이 필요한 경우

개발자 수정본에 기능을 추가하기 위해 재생성하지 않는다. 새 템플릿 결과가 필요하면 다음 중 하나를 선택한다.

- 새 식별자나 별도 위치에 신규 생성 후 필요한 부분만 수동 반영
- 기존 화면을 폐기하기로 결정하고 버전 관리에 보존한 뒤 완전 재생성

`ScaffoldRegenerateMain`은 병합 도구가 아니다. 모든 활성 case의 기존 수정본을 버리고 새 템플릿 결과로 교체할 때 사용한다. 수정 내용을 보존하는 부분 갱신 용도로는 사용하지 않는다.
