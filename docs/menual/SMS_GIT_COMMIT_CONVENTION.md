## 1. 목적과 적용 원칙

이 규칙은 커밋 제목만 보고도 변경 영역과 목적을 파악하고, 코드 리뷰·장애 추적·원복·릴리스 노트 작성을 일관되게 하기 위한 팀 표준이다.

- 신규 커밋부터 적용하며 기존 이력에는 소급 적용하지 않는다.
- `main`, `master`, `develop`, `release/*` 등 공유 브랜치에 남는 커밋은 이 규칙을 따른다.
- PR을 Squash Merge하면 PR 제목이 최종 커밋 제목이 되므로 PR 제목에도 같은 규칙을 적용한다.
- 자동 생성된 Merge 커밋과 팀에서 승인한 봇 커밋만 예외로 한다.
- 현재 저장소에는 커밋 메시지를 자동 차단하는 `commit-msg` 훅이나 commitlint 설정이 없다. 작성자와 리뷰어가 이 문서를 기준으로 확인한다.

### 핵심 원칙

1. 한 커밋에는 하나의 논리적 목적만 담는다.
2. 제목에는 변경 파일이 아니라 변경 결과를 적는다.
3. 기능과 그 기능을 검증하는 테스트는 같은 커밋에 포함할 수 있다.
4. 관련 없는 포맷 변경, 문서 변경, 설정 변경을 기능 커밋에 섞지 않는다.
5. 가능한 한 각 커밋이 빌드·테스트 가능한 상태가 되도록 한다.

## 2. 빠른 작성법

가장 많이 사용하는 형식은 다음과 같다.

```text
<type>(<scope>): <summary>
```

예시:

```text
feat(menu): 하위 메뉴 등록 기능 추가
fix(auth): 비활성 메뉴의 접근 권한 차단
test(scaffold): MSSQL 생성 결과 회귀 테스트 추가
docs: 폐쇄망 반입 절차 보완
```

작성 순서:

1. 변경이 기능 추가인지, 결함 수정인지 먼저 판단해 `type`을 고른다.
2. 변경 영역이 명확하면 `scope`를 적는다.
3. 사용자가 얻게 된 결과 또는 해결된 문제를 `summary`에 적는다.
4. 제목만으로 이유와 영향이 불명확하면 본문을 추가한다.
5. 이슈 번호, 호환성 변경, 원복 대상은 footer에 적는다.

## 3. 커밋 메시지 구조

전체 형식:

```text
<type>(<scope>)!: <summary>

<body>

<footer>
```

각 요소의 필수 여부는 다음과 같다.

| 요소 | 필수 여부 | 설명 |
|---|---|---|
| `type` | 필수 | 변경의 성격을 영문 소문자로 표시한다. |
| `scope` | 선택·권장 | 변경된 업무 또는 모듈 영역을 표시한다. |
| `!` | 조건부 필수 | 이전 사용 방식과 호환되지 않는 변경에 표시한다. |
| `summary` | 필수 | 변경 결과를 한 줄로 요약한다. |
| `body` | 조건부 | 변경 이유, 구현 판단, 영향, 검증 내용을 설명한다. |
| `footer` | 조건부 | 이슈, Breaking Change, 원복 대상 등을 기록한다. |

`scope`, `!`, body, footer는 상황에 따라 생략할 수 있지만 `type`과 `summary`는 항상 작성한다.

### 본문이 없는 간단한 변경

```text
docs(api): 발송 API 오류 응답 예시 추가
```

### 본문과 이슈가 있는 변경

```text
fix(validation): 제목 누락 오류의 필드 매핑 수정

서버 오류 응답의 field 값을 화면 input name과 동일하게 맞춘다.
검증 실패 후에도 오류 메시지와 저장 버튼 상태가 유지되도록 한다.

Refs: SMS-142
```

### 명령행 작성 예시

본문이 짧으면 `-m`을 여러 번 사용한다. 첫 번째 `-m`은 제목, 두 번째부터는 본문 문단이 된다.

```bash
git commit -m "feat(api): 예약 발송 요청 검증 추가" \
  -m "필수값과 예약 시각의 유효성을 요청 DTO에서 검증한다." \
  -m "Refs: SMS-142"
```

본문이 길면 편집기를 사용하는 편이 안전하다.

```bash
git commit
```

## 4. Type 규칙

허용하는 type은 다음과 같다.

| Type | 사용 기준 | 예시 |
|---|---|---|
| `feat` | 새로운 사용자 기능, 업무 기능, API 추가 | `feat(api): 직원 조회 REST API 추가` |
| `fix` | 잘못된 동작이나 결함 수정 | `fix(menu): 하위 메뉴 정렬 순서 오류 수정` |
| `refactor` | 외부 동작 변화가 없는 코드 구조 개선 | `refactor(common): 오류 응답 변환 로직 분리` |
| `perf` | 동작을 유지하면서 성능 또는 자원 사용 개선 | `perf(db): 발송 이력 조회 쿼리 최적화` |
| `test` | 운영 코드 변화 없이 테스트만 추가·수정 | `test(menu): 캐시 리비전 갱신 검증 추가` |
| `docs` | 문서만 추가·수정 | `docs: Git 커밋 규칙 보완` |
| `style` | 공백, 정렬, formatter 등 동작과 무관한 변경 | `style(web): 템플릿 들여쓰기 정리` |
| `build` | Maven, 의존성, 패키징 방식 변경 | `build(deps): JDBC 드라이버 버전 갱신` |
| `ci` | CI/CD 작업과 배포 파이프라인 변경 | `ci: 배포 전 통합 테스트 단계 추가` |
| `chore` | 위 분류에 속하지 않는 저장소 유지보수 | `chore(config): 로컬 설정 예시 정리` |
| `revert` | 기존 커밋을 이력으로 원복 | `revert(menu): 하위 메뉴 등록 변경 되돌림` |

### Type 선택 기준

- 사용자에게 새로운 동작이 제공되면 `feat`를 사용한다.
- 의도와 다르게 동작하던 것을 바로잡으면 `fix`를 사용한다.
- 동작은 같고 내부 구조만 바뀌면 `refactor`를 사용한다.
- 테스트가 기능 변경 커밋에 딸린 검증이라면 기능과 같은 커밋에 포함하고 `feat` 또는 `fix`를 사용한다.
- 테스트 파일만 독립적으로 변경하면 `test`를 사용한다.
- 화면 디자인이나 사용자 동작이 바뀌면 `style`이 아니라 `feat` 또는 `fix`를 사용한다.
- 보안 결함 수정은 `fix(security)`, 보안 기능 추가는 `feat(security)`를 사용한다.
- 운영 동작이 바뀌는 설정 변경을 `chore`로 숨기지 않는다. 동작 변화에 따라 `feat`, `fix`, `build` 중 하나를 고른다.
- `chore`를 분류가 애매한 모든 변경의 기본값으로 사용하지 않는다.

다음 단어는 type으로 사용하지 않는다.

```text
add, update, change, feature, bugfix, hotfix, release, wip
```

## 5. Scope 규칙

Scope는 어떤 영역의 변경인지 빠르게 찾기 위한 값이다. 변경 영역이 명확하면 사용하고, 저장소 전체에 걸친 변경이면 생략할 수 있다.

### 작성 규칙

- 영문 소문자를 사용한다.
- 두 단어 이상이면 kebab-case를 사용한다.
- 파일명보다 업무 도메인 또는 공통 모듈명을 우선한다.
- 한 커밋에서 여러 scope가 필요하다면 커밋 분리가 가능한지 먼저 검토한다.
- `misc`, `etc`, `temp`처럼 의미가 불명확한 scope는 사용하지 않는다.

### 프로젝트 권장 Scope

| Scope | 대상 |
|---|---|
| `api` | 외부 연계 REST API와 공통 API 계약 |
| `auth` | 로그인, 인증, 세션 처리 |
| `security` | Spring Security, API Key, 접근 제어 |
| `menu` | 메뉴 계층, 메뉴 권한, 메뉴 캐시 |
| `scaffold` | Query Scaffold와 생성 템플릿 |
| `sms` | SMS 발송, 캠페인, 발송 이력 |
| `employee` | 직원 조회와 직원 데이터 연계 |
| `basic` | 공지사항 등 기본 업무 화면 |
| `system` | 시스템 관리 화면과 기능 |
| `common` | 여러 업무에서 사용하는 공통 JavaScript·Java 코드 |
| `validation` | 입력 검증과 오류 표시 계약 |
| `db` | 공통 DB 스키마, seed, SQL 변경 |
| `config` | 프로파일과 애플리케이션 설정 |
| `web` | 특정 도메인에 속하지 않는 템플릿·정적 화면 자산 |
| `deps` | 의존성 변경 |

예시:

```text
feat(menu): 3단계 메뉴 계층 등록 지원
fix(scaffold): MSSQL 컬럼 메타데이터 변환 오류 수정
refactor(common): 모달 초기화 로직 분리
```

Scope를 생략해도 되는 예시:

```text
docs: 프로젝트 문서 인덱스 갱신
ci: Maven 테스트 결과 보관 단계 추가
```

## 6. Summary 규칙

Summary는 제목의 핵심이며 변경 결과를 구체적으로 설명해야 한다.

### 필수 규칙

- 한국어로 작성한다. 제품명, 클래스명, 표준 기술 용어는 영문을 사용할 수 있다.
- 문장 끝에 마침표를 붙이지 않는다.
- `수정`, `변경`, `작업`, `최종`만 단독으로 쓰지 않는다.
- 무엇이 어떻게 달라졌는지 드러나게 작성한다.
- Summary는 50자 이내를 권장하고 제목 전체는 72자 이내를 권장한다.
- 이슈 번호, 작업자 이름, 날짜는 summary에 넣지 않고 footer 또는 이슈 시스템에서 관리한다.

### 권장 종결 표현

```text
추가, 수정, 개선, 분리, 통합, 제거, 차단, 허용, 보강, 최적화
```

### 좋은 예와 나쁜 예

| 나쁜 제목 | 문제 | 개선한 제목 |
|---|---|---|
| `fix: 수정` | 대상과 결과를 알 수 없음 | `fix(menu): 비활성 메뉴의 URL 접근 차단` |
| `feat: 메뉴 작업` | 구현 결과가 불명확함 | `feat(menu): 하위 메뉴 등록과 순서 변경 지원` |
| `update: 파일 변경` | 허용되지 않은 type이며 의미가 없음 | `docs: 폐쇄망 반입 파일 목록 갱신` |
| `chore: 최종` | 변경 목적을 추적할 수 없음 | `test(scaffold): MSSQL 골든 파일 검증 추가` |
| `style: 버튼 색상 변경` | 사용자 화면 변화는 style이 아님 | `fix(web): 비활성 저장 버튼 색상 대비 개선` |

## 7. Body와 Footer 규칙

### Body를 작성해야 하는 경우

다음 중 하나에 해당하면 본문을 작성한다.

- 변경 이유가 제목만으로 드러나지 않는 경우
- DB 스키마, 운영 설정, 인증·권한, 보안에 영향을 주는 경우
- 다른 구현 방법 대신 현재 방법을 선택한 이유가 있는 경우
- 반입·배포 순서나 데이터 마이그레이션이 필요한 경우
- 장애 대응이나 재현 조건을 기록해야 하는 경우

본문에는 코드의 상세 동작을 반복하기보다 다음 내용을 적는다.

1. 왜 변경했는가
2. 어떤 방식으로 해결했는가
3. 영향 범위와 주의사항은 무엇인가
4. 어떤 테스트로 검증했는가

예시:

```text
feat(menu): 메뉴 변경 시 정적 메뉴 캐시 갱신

메뉴 추가 후 기존 세션에서 변경 내용이 바로 보이지 않는 문제를 해결한다.
MenuCacheRevision 값을 응답 캐시 키에 반영하고 메뉴 저장 성공 시 리비전을 증가시킨다.

검증: MenuManageServiceTest, MenuCacheRevisionTest
```

### Footer 규칙

Footer는 본문과 한 줄을 비운 뒤 작성한다.

```text
Refs: SMS-142
Fixes: SMS-143
```

- 관련 이슈를 연결만 하면 `Refs:`를 사용한다.
- 해당 커밋으로 이슈가 종료되면 팀 이슈 시스템 규칙에 맞춰 `Fixes:`를 사용한다.
- Azure DevOps Work Item은 환경에 맞게 `AB#1234` 또는 `Fixes AB#1234` 형식을 사용할 수 있다.
- 민감한 장애 정보나 고객 데이터는 이슈 번호로만 연결하고 커밋 메시지에 직접 적지 않는다.

### Breaking Change

API 요청·응답, DB 계약, 설정 키, 공개된 공통 함수처럼 기존 사용 방식과 호환되지 않는 변경은 제목의 `!`와 footer의 `BREAKING CHANGE:`를 모두 작성한다.

```text
feat(api)!: 직원 조회 응답의 부서 식별자 형식 변경

부서 식별자를 숫자형 단일 값에서 문자열 복합키로 변경한다.
기존 API 사용자는 DEP_ID 직렬화와 비교 로직을 수정해야 한다.

BREAKING CHANGE: departmentId가 number에서 string으로 변경된다.
Refs: SMS-210
```

## 8. 커밋 분리 기준

### 같은 커밋에 포함할 수 있는 변경

- 기능 구현 코드와 그 기능의 단위 테스트
- 화면 템플릿, 전용 JavaScript, 전용 CSS, Controller·Service·Mapper 등 하나의 화면을 완성하는 파일
- 스캐폴드 템플릿 변경과 이에 따라 갱신된 골든 테스트
- DB 컬럼 변경과 해당 변경 없이는 동작하지 않는 Mapper·DTO 수정

### 별도 커밋으로 나눠야 하는 변경

- BASE 공통 코드 변경과 개별 업무 화면 생성
- 기능 변경과 무관한 대규모 formatter 적용
- 서로 독립적으로 배포·원복할 수 있는 두 기능
- 리팩터링과 사용자 동작 변경이 각각 독립적인 경우
- 문서 정리와 운영 코드 변경의 목적이 직접 연결되지 않은 경우
- 의존성 버전 변경과 그 의존성을 사용하지 않는 기능 변경

### 프로젝트 기본 단위

- 화면 1개 생성은 커밋 1개를 기본으로 한다.
- 화면 커밋에는 해당 화면의 Scaffold 산출물, 테스트, 메뉴 SQL을 함께 포함할 수 있다.
- BASE 공통 코드 수정과 화면 생성은 분리한다.
- BASE 공통 코드 커밋은 원칙적으로 전체 `mvn test` 통과를 전제로 한다.

분리 예시:

```text
# 커밋 1
refactor(common): 메뉴 캐시 키 생성 로직 분리

# 커밋 2
feat(menu): 하위 메뉴 등록 기능 추가

# 커밋 3
docs(menu): 메뉴 관리 운영 절차 보완
```

## 9. 프로젝트 작업별 예시

### 메뉴와 권한

```text
feat(menu): 하위 메뉴 등록과 계층 조회 지원
fix(menu): 그룹 메뉴의 화면 권한 판정 제외
test(menu): 메뉴 저장 후 캐시 리비전 갱신 검증 추가
```

### REST API

```text
feat(api): API Key 기반 직원 조회 엔드포인트 추가
fix(api): 존재하지 않는 직원 조회를 404로 변환
test(employee): 직원 조회 서비스의 빈 결과 처리 검증
```

### Query Scaffold

```text
feat(scaffold): MSSQL 2017 방언 추가
fix(scaffold): 예약어 컬럼의 대괄호 이스케이프 적용
test(scaffold): MSSQL Mapper XML 골든 회귀 테스트 추가
```

### 화면과 공통 JavaScript

```text
feat(system): 메뉴 상세 편집 모달 추가
fix(common): 중첩 모달의 확인창 표시 순서 수정
refactor(common): 필드 포맷 초기화 로직 모듈화
```

### DB와 설정

```text
feat(db): 메뉴 그룹 유형 G의 계층 seed 추가
fix(config): local 프로파일의 스캐폴드 DB 플랫폼 적용
build(deps): MSSQL JDBC 드라이버 의존성 추가
```

### 문서와 반입 파일

```text
docs: 폐쇄망 반입 대상과 삭제 절차 갱신
docs(git): 커밋 메시지 작성 규칙 보완
chore: 폐쇄망 반입 ZIP 재생성
```

### Body를 포함한 실제 형태

```text
feat(scaffold): MSSQL 2017 방언 추가

ScaffoldDialect에 MSSQL 식별자 quoting과 페이징 구문을 추가한다.
Oracle 생성 결과는 유지하고 MSSQL 골든 파일로 방언별 출력을 검증한다.

검증: ScaffoldOutputGoldenTest#mssql
```

## 10. 커밋 전 점검과 검증

### 1단계: 변경 범위 확인

```bash
git status --short
git diff --stat
git diff
```

### 2단계: 필요한 파일만 Stage

```bash
git add src/main/java/com/scbk/sms/service/menu/MenuCacheRevision.java
git add src/test/java/com/scbk/sms/service/menu/MenuCacheRevisionTest.java
```

전체 파일을 무조건 `git add .`로 올리기보다 커밋 목적에 맞는 경로를 명시한다.

### 3단계: Stage 결과 재확인

```bash
git status --short
git diff --cached --stat
git diff --cached
git diff --cached --check
```

반드시 확인할 항목:

- 커밋 목적과 무관한 파일이 포함되지 않았는가
- `.env.local`, 실제 비밀번호, 토큰, 인증정보가 포함되지 않았는가
- `target/`, 로그, IDE 임시 파일, 개인 설정 파일이 포함되지 않았는가
- 삭제·이름 변경이 의도한 것인가
- 테스트 파일과 DB 변경 파일이 누락되지 않았는가

### 4단계: 가장 좁은 관련 테스트 실행

```bash
mvn -Dtest=MenuManageServiceTest,MenuCacheRevisionTest test
```

공통 코드, 빌드 설정, 전체 생성 템플릿처럼 영향 범위가 넓으면 전체 테스트를 실행한다.

```bash
mvn test
```

문서 인덱스만 변경한 경우에도 관련 계약 테스트가 있으면 실행한다.

```bash
mvn -Dtest=ManualDocumentationContractTest test
```

### 5단계: 메시지 작성과 최종 확인

```bash
git commit -m "feat(menu): 메뉴 변경 시 캐시 리비전 갱신"
git show --stat --oneline HEAD
```

## 11. 수정·원복·병합 규칙

### 아직 공유하지 않은 마지막 커밋 수정

누락 파일이나 메시지만 바로잡을 때 사용한다.

```bash
git add <누락된-파일>
git commit --amend
```

이미 원격 공유 브랜치에 push한 커밋은 임의로 amend하거나 rebase하지 않는다. 다른 작업자의 기준 SHA가 바뀌기 때문이다.

### 아직 공유하지 않은 여러 커밋 정리

```bash
git rebase -i HEAD~3
```

`fixup!`, `squash`, `reword`는 로컬 브랜치 정리 과정에서만 사용하고 공유 이력에는 임시 메시지를 남기지 않는다.

### 공유된 커밋 원복

공유 이력을 삭제하지 않고 `git revert`를 사용한다.

```bash
git revert <commit-sha>
```

메시지 예시:

```text
revert(menu): 하위 메뉴 등록 변경 되돌림

폐쇄망 운영 DB의 메뉴 유형 데이터 전환이 완료되지 않아 이전 동작으로 복구한다.

Reverts: a1b2c3d4
Refs: SMS-245
```

### Merge와 Squash

- 일반 Merge를 사용하면 개별 커밋 메시지와 자동 생성 Merge 커밋을 유지한다.
- Squash Merge를 사용하면 PR 제목이 최종 커밋 제목이 되므로 규칙에 맞게 작성한다.
- 여러 목적의 커밋을 Squash할 때는 최종 제목이 전체 변경의 주목적을 설명해야 한다.
- force push는 사용자가 명시적으로 요청하고 영향 범위를 확인한 경우에만 수행한다.

## 12. 금지 사항

### 의미 없는 메시지

다음 메시지는 공유 이력에 남기지 않는다.

```text
WIP
수정
최종
진짜 최종
temp
test
fixup!
작업중
```

### 민감정보 포함

커밋 메시지와 변경 파일에 다음 정보를 포함하지 않는다.

- 실제 전화번호, 고객명, 메시지 원문
- 비밀번호, API Key, 토큰, 세션 값
- DB·LDAP·발송사 운영 자격 증명
- 실제 `.env` 파일과 개인 인증서
- 외부 공개가 제한된 장애 상세 데이터

테스트 데이터는 실제 정보와 혼동되지 않는 명백한 가상값을 사용한다.

### 위험한 이력 변경

- 공유 브랜치에서 합의 없이 `git push --force`하지 않는다.
- 장애가 난 변경을 이력에서 지우기 위해 reset하지 않는다.
- 검증하지 않은 대량 변경을 하나의 커밋으로 묶지 않는다.
- 다른 사람의 변경을 자신이 작성한 것처럼 amend하지 않는다.

## 13. 최종 체크리스트

커밋 직전에 아래 항목을 확인한다.

- [ ] 한 커밋에 하나의 논리적 목적만 들어 있다.
- [ ] 제목이 `<type>(<scope>): <summary>` 형식을 따른다.
- [ ] Type이 허용 목록에 포함된다.
- [ ] Summary만 보고 변경 결과를 이해할 수 있다.
- [ ] 제목 끝에 마침표가 없고 임시 표현을 사용하지 않았다.
- [ ] 관련 없는 파일과 개인 설정 파일이 Stage에 없다.
- [ ] 비밀번호, 토큰, 고객 정보 등 민감정보가 없다.
- [ ] 필요한 테스트와 DB·설정·문서 변경이 누락되지 않았다.
- [ ] 가장 좁은 관련 테스트를 실행했다.
- [ ] 공통 코드 변경이면 전체 테스트 결과를 확인했다.
- [ ] 이슈 번호와 Breaking Change가 필요한 경우 footer에 기록했다.
- [ ] `git diff --cached`로 실제 커밋 내용을 최종 확인했다.

## 요약

```text
좋은 커밋 = 하나의 목적 + 명확한 type/scope + 결과 중심 summary + 필요한 검증 기록
```

가장 중요한 기준은 형식 자체보다 **나중에 이 커밋만 보고 변경 이유와 원복 범위를 판단할 수 있는가**이다.
