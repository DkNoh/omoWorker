# 프로메테우스 작업 요청서: 스캐폴드 테스트 #3

> 문서 성격: 실행 전 작업 계획 및 검토 기록. 현행 설계 계약과 개발 매뉴얼의 원본이 아니다.

## 확정 전제

- 현재 메뉴에 등록된 업무 화면은 테스트·참고 화면이며 운영 호환이나 마이그레이션 대상에서 제외한다.
- `scaffold-templates/**/*.tpl`은 신규 화면의 최초 생성 원본이다.
- 한 번 적용된 생성물은 개발자가 직접 수정해 소유하며 템플릿과 계속 동기화하지 않는다.
- 재생성은 사용자 수정 내용을 병합하는 갱신이 아니라 기존 수정본을 폐기하고 새로 만드는 작업이다.
- Scaffold에 없는 업무 기능은 생성된 기본 레이아웃과 공통 자산 위에 개발자가 추가한다.

현재 저장소의 스캐폴드/코드 생성기와 관련 문서를 분석하고 아래 6개 항목을 진행해줘.

먼저 저장소의 작업 지침(`AGENTS.md`, `README`, 개발 가이드 등)을 확인하고, 실제 코드 구조와 기존 설계 의도를 파악한 뒤 작업해야 한다. 단순 문자열 치환이나 전체 XML 일괄 변경은 금지한다.

## 공통 진행 원칙

1. 각 항목의 관련 소스, 템플릿, 생성 결과물, 테스트를 먼저 추적한다.
2. 변경 전에 현재 동작과 문제 원인을 정리한다.
3. 현재 테스트 화면의 하위 호환은 완료 조건으로 두지 않는다. 다만 앞으로 생성될 코드의 SQL 정확성, 보안과 공통 계약은 유지한다.
4. 자동 변환이 위험한 경우 억지로 수정하지 말고 다음 중 하나로 처리한다.
   - 안전 조건을 만족하는 경우에만 자동 처리
   - 수동 처리 대상으로 분류
   - 변경 보류 후 구체적인 위험과 근거 보고
5. 템플릿과 생성 로직을 우선 수정한다. 현재 테스트 화면은 필요하면 폐기 후 다시 만들 수 있지만, 개발자 소유 업무 화면에는 템플릿 변경을 일괄 반영하지 않는다.
6. 변경 후 관련 단위 테스트, 통합 테스트 또는 생성 결과 검증 테스트를 실행한다.
7. 문서만 요구된 항목은 권한 시스템 등의 런타임 구조를 임의로 마이그레이션하지 않는다.

## 1. 검색 조건 `WHERE` 절을 서브쿼리 내부로 이동

### 현재 구조

```xml
SELECT A.*
FROM (
    <include refid="baseQuery"/>
) A
<include refid="searchConditions"/>
...
```

### 목표 구조

```xml
SELECT A.*
FROM (
    <include refid="baseQuery"/>
    <include refid="searchConditions"/>
) A
...
```

검색 조건이 바깥쪽 쿼리가 아니라 실제 데이터를 조회하는 내부 서브쿼리에 적용되도록 스캐폴드 템플릿을 수정한다.

### 조사 및 구현 조건

- 관련 MyBatis XML 템플릿과 템플릿 생성 로직을 모두 찾는다.
- `searchConditions`가 참조하는 컬럼과 별칭이 내부 쿼리에서도 유효한지 확인한다.
- 외부 별칭 `A`만 참조하는 조건은 그대로 내부로 옮기면 SQL 오류가 발생할 수 있으므로 자동 변경하지 않는다.
- 내부 이동으로 인해 페이징, 정렬, 윈도우 함수, 조인 결과가 달라지는지 확인한다.
- 동일한 템플릿 패턴이 여러 DBMS용으로 존재하면 DBMS별 구문도 확인한다.
- 안전한 공통 패턴은 템플릿에 반영하고, 별칭이나 쿼리 구조 때문에 안전하지 않은 패턴은 수동 처리 또는 스킵 대상으로 명확히 기록한다.

### 완료 조건

- 새로 생성한 기본 조회 SQL에서 `searchConditions`가 서브쿼리 내부에 위치한다.
- 조건이 있는 경우와 없는 경우 모두 정상 SQL이 생성된다.
- 페이징과 정렬 결과가 기존 요구사항과 일치한다.
- 별칭이 포함된 사례를 테스트한다.

## 2. COUNT 쿼리 단순화 가능성 검토 및 조건부 반영

### 현재 구조

```xml
SELECT COUNT(1)
FROM (
    <include refid="baseQuery"/>
    <include refid="searchConditions"/>
) A
```

현재 COUNT 쿼리는 목록 조회용 SELECT 전체를 서브쿼리로 감싸고 있다.

### 목표 방향

불필요한 SELECT 컬럼, 정렬, 페이징 등을 제외하고 COUNT에 필요한 `FROM`, `JOIN`, 검색 조건만 사용하도록 개선한다.

예시:

```xml
SELECT COUNT(1)
FROM
    <include refid="baseTable"/>
<include refid="searchConditions"/>
```

실제 MyBatis 문법에 맞게 `baseTable` include의 책임과 포함 범위를 설계해야 한다. `baseTable`은 단순 테이블명만 의미할 수도 있고, COUNT 결과에 필요한 JOIN까지 포함해야 할 수도 있으므로 기존 쿼리를 분석한 뒤 결정한다.

### 반드시 확인할 위험 요소

다음 구조는 단순 COUNT로 바꾸면 결과가 달라질 수 있다.

- `DISTINCT`
- `GROUP BY` 또는 `HAVING`
- `UNION`
- 집계 쿼리
- 조인으로 인한 중복 행
- 계산 컬럼이나 서브쿼리가 검색 조건에 필요한 경우
- 목록 쿼리 자체가 한 행으로 축약되는 경우
- 내부와 외부에서 사용하는 컬럼 별칭이 다른 경우

### 구현 원칙

- 단순 단일 테이블 또는 의미가 보존되는 쿼리에만 최적화 구조를 적용한다.
- 복잡한 쿼리는 기존 `COUNT FROM (subquery)` 방식을 유지한다.
- 생성기가 쿼리 구조를 신뢰성 있게 구분하지 못한다면 자동 최적화를 강행하지 않는다.
- 필요하다면 “기본 COUNT 템플릿”과 “복합 쿼리용 COUNT 템플릿”을 분리한다.
- 공수나 회귀 위험이 큰 경우 변경을 보류하고 수동 처리 기준을 문서화한다.

### 완료 조건

- 목록 결과 건수와 COUNT 결과가 항상 일치한다.
- 단순 쿼리에서는 불필요한 SELECT 및 정렬이 제거된다.
- 복합 쿼리 사례에는 기존 안전한 COUNT 방식이 유지된다.
- 실행 계획 또는 최소한 생성 SQL 비교를 통해 개선 효과와 안전성을 확인한다.

## 3. 연속 도메인 생성 시 PK·잠금·메뉴 등록 옵션 상태 갱신 문제

최초 도메인을 등록한 뒤 같은 화면이나 같은 세션에서 다른 도메인을 연속 생성하면 다음 옵션이 새 도메인 설정에 맞게 활성화되거나 초기화되지 않는 문제가 있는지 조사한다.

- PK 관련 옵션
- 잠금 관련 옵션
- 메뉴 등록 옵션

### 조사 범위

- 프런트엔드 폼 상태 초기화
- 도메인 선택 변경 이벤트
- 이전 도메인의 상태가 남는지 여부
- 기본값 계산 로직
- 백엔드 요청 DTO 및 세션 상태
- 생성 단계 간 공유 객체 또는 전역 상태
- 옵션의 표시 상태와 실제 전송 값 불일치 여부

### 기대 동작

- 새로운 도메인 생성을 시작하면 이전 도메인의 옵션 상태가 남지 않아야 한다.
- 새 도메인의 메타데이터에 따라 각 옵션의 활성화 여부와 기본값이 다시 계산되어야 한다.
- 비활성화된 옵션 값이 요청 데이터에 숨어서 전달되지 않아야 한다.
- 뒤로 가기, 재선택, 연속 생성 등의 흐름에서도 상태가 일관되어야 한다.

### 테스트 시나리오

1. PK/잠금/메뉴 등록 옵션을 활성화한 도메인 생성
2. 화면을 새로고침하지 않고 두 번째 도메인 생성 시작
3. 두 번째 도메인은 서로 다른 옵션 조합 선택
4. UI 표시, 전송 payload, 최종 생성 결과가 두 번째 설정과 일치하는지 확인
5. 반대 순서의 옵션 조합도 확인

원인과 수정 범위가 명확하고 회귀 위험이 낮으면 반영한다. 상태 구조를 전면 개편해야 하거나 공수가 큰 경우에는 변경을 보류하고 재현 방법, 원인, 권장 수정안을 보고한다.

## 4. 메뉴 캐싱 및 로그인 세션의 메뉴 갱신 문제

### 현재 추정 동작

- 로그인 시 메뉴를 조회하여 세션에 저장한다.
- 세션에 메뉴 정보가 있으면 메뉴 테이블을 다시 조회하지 않는다.
- 로그인 상태에서 메뉴가 등록·수정·삭제되어도 다음 화면에 바로 반영되지 않을 수 있다.
  - 좌측 사이드바 메뉴(LNB)
  - 시스템 관리의 메뉴 트리

먼저 실제 구현을 추적하여 이 동작이 맞는지 확인한다. 세션 고정이 의도된 보안 또는 UX 정책이라면 임의로 변경하지 말고 근거를 보고한다.

### 개선 방향

의도된 동작이 아니라면 Spring Cache 기반 구조 또는 그에 준하는 일관된 캐시 전략을 검토한다.

예시 방향:

- 메뉴 최초 조회: `@Cacheable`
- 메뉴 등록·수정·삭제 성공 후: `@CacheEvict`
- 트랜잭션이 실제 커밋된 이후 캐시가 무효화되도록 처리
- 필요하면 `allEntries = true` 또는 영향받은 키만 제거

### 설계 시 주의사항

단순히 세션 캐시를 Spring Cache로 바꾸는 것만으로 현재 로그인한 사용자의 메뉴가 즉시 갱신된다고 가정하면 안 된다.

다음을 확인한다.

- 메뉴가 사용자, 역할, 조직, 테넌트, 언어별로 달라지는지
- 캐시 키에 어떤 사용자 문맥이 포함되어야 하는지
- 메뉴 원본 트리와 사용자별 권한 필터링 결과 중 무엇을 캐싱할지
- 메뉴 변경 후 기존 HTTP 세션에 저장된 메뉴가 계속 사용되는지
- LNB가 메뉴 정보를 다시 요청할 수 있는지
- 메뉴 관리 화면과 LNB가 같은 캐시 데이터를 사용하는지
- 여러 서버 인스턴스에서 캐시 무효화가 전파되는지

현재 세션에 메뉴 객체를 계속 보관하는 구조라면 다음 대안을 비교하여 가장 작은 안전한 변경을 선택한다.

- 세션 저장을 제거하고 캐시 기반 조회로 통일
- 메뉴 변경 시 관련 세션 데이터도 무효화
- 메뉴 버전을 비교하여 변경 시 재조회
- 프런트엔드에서 변경 완료 후 메뉴를 재요청

### 완료 조건

- 메뉴 등록·수정·삭제 후 관리 화면의 메뉴 트리가 최신 상태로 조회된다.
- 현재 로그인 사용자의 LNB도 정해진 시점에 최신 상태로 갱신된다.
- 사용자별 권한이 다른 메뉴가 서로 섞이지 않는다.
- 캐시 무효화는 DB 트랜잭션 성공 후 이루어진다.
- 메뉴 변경 실패 시 정상 캐시까지 제거하는 부작용이 없어야 한다.
- 캐시 적용 전후 쿼리 횟수와 동작을 테스트한다.

## 5. TO-BE 역할·권한 체계 가이드 작성

현재 권한 체계의 레벨과 기능 권한을 먼저 코드, DB 스키마, 초기 데이터, 권한 체크 로직에서 조사한다.

### AS-IS 예시

레벨:

- 슈퍼관리자(1)
- 관리자(2)
- 일반사용자(3)
- 계정관리자(4)

기능 권한:

- SMS 조회
- SMS 승인
- 통계
- 기타 업무별 권한

현재 구조는 사용자에게 레벨 또는 개별 기능 권한을 직접 부여하는 방식인지 확인한다.

### TO-BE 방향

사용자에게 권한을 직접 나열하기보다는 역할을 부여하고, 역할에 기능 권한을 매핑하는 RBAC 형태로 정리한다.

역할 예시:

- 시스템 관리자: `ROLE_ADMIN`
- 업무 관리자: `ROLE_MANAGER`
- 일반 사용자: `ROLE_USER`
- 조회 사용자: `ROLE_VIEWER`

기능 권한 예시:

- 조회
- 등록
- 수정
- 삭제
- 승인
- 취소
- 다운로드
- 마스킹

위 이름을 그대로 확정하지 말고 실제 AS-IS 권한과 업무 기능을 분석하여 필요한 TO-BE 역할과 권한 메타데이터를 정의한다.

### 문서에 포함할 내용

- AS-IS 레벨 및 기능 권한 목록
- 현재 권한 부여·검사 흐름
- AS-IS의 문제점과 중복 구조
- TO-BE 역할과 기능 권한의 정의
- 역할과 권한의 매핑 표
- 사용자–역할–권한 관계
- 역할명 및 권한 코드 네이밍 규칙
- 메뉴 접근 권한과 API 권한의 관계
- 복수 역할을 가진 사용자의 권한 합성 규칙
- 승인·다운로드·마스킹과 같은 특수 권한 처리
- 기존 레벨에서 TO-BE 역할로의 매핑 예시
- 점진적인 마이그레이션 방법
- 신규 도메인/기능 개발 시 권한 추가 기준
- 예제 코드 또는 의사 코드

이 항목의 기본 범위는 “가이드 작성”이다. 별도 요구가 없다면 실제 인증·인가 시스템 전체를 TO-BE 구조로 마이그레이션하지 않는다.

## 6. 도메인 설계 및 소스 생성 기준 가이드 정비

기존 문서인 다음 파일을 찾아 내용을 검토한다.

```text
docs/base/domain-boundary-guide.md
```

파일 경로가 다르거나 문서가 없다면 관련 문서 구조를 탐색하고 결과를 보고한다.

### 문서 목적

개발자가 신규 기능을 만들 때 다음을 일관되게 판단할 수 있도록 해야 한다.

- 하나의 도메인으로 묶을 범위
- 도메인을 분리해야 하는 기준
- 스캐폴드로 생성할 수 있는 소스의 범위
- 자동 생성 이후 개발자가 직접 작성해야 하는 영역
- 도메인 간 의존과 참조 원칙
- 공통 코드와 업무 도메인의 구분
- 조회 모델과 변경 모델의 분리 여부
- 트랜잭션 경계
- 패키지 및 클래스 네이밍
- Controller, Service, Repository/Mapper, DTO, Entity/Model 생성 기준
- 메뉴 및 권한과 도메인의 연결 기준
- 복합 쿼리나 외부 연동 등 스캐폴드 적용이 부적절한 사례

### 필요한 작업

- 기존 `domain-boundary-guide.md`의 중복, 모호한 표현, 누락된 판단 기준을 정리한다.
- 추상적인 설명만 두지 말고 실제 프로젝트 구조를 반영한 예시를 추가한다.
- “하나의 도메인으로 생성할 사례”와 “별도 도메인으로 분리할 사례”를 비교한다.
- 권장 구조뿐 아니라 금지하거나 주의해야 할 안티패턴도 포함한다.
- 프로젝트의 메뉴얼 또는 문서 인덱스를 찾아 이 가이드를 포함하거나 링크한다.
- 존재하지 않는 메뉴얼 구조를 임의로 만들기 전에 현재 문서 빌드 및 네비게이션 방식을 확인한다.
